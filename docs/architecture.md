## 1. Назначение, границы, принципы

### 1.1. Задачи

Централизованный сбор данных с ПК, принадлежащих организации:

- **метрики** — загрузка CPU, использование RAM, свободное место на томах;
- **инвентаризация** — ОС, производитель и модель, CPU, модули RAM, физические диски и тома, сетевые адаптеры;
- **установленное ПО** — из ключей реестра Uninstall (см. 4.2).

На сервере: веб-интерфейс (устройства, метрики, ПО), настраиваемые алерты, уведомления по email и webhook, журнал событий и аудит действий.

Целевой масштаб MVP — до 100 ПК. Запас без смены стека — порядка 5 000 ПК; путь дальше описан в 10.5.

### 1.2. Чего система не делает — осознанно

| Не делает | Зачем это ограничение |
|---|---|
| Не выполняет команды и скрипты, не устанавливает ПО, не даёт удалённого рабочего стола и доступа к файлам | Нет канала доставки кода на ПК: компрометация сервера не превращается в компрометацию парка |
| Не открывает входящие порты на ПК | На рабочих станциях нечего сканировать и атаковать по сети |
| Не собирает пользовательские данные: содержимое файлов, историю браузера, снимки экрана, нажатия клавиш, заголовки окон, командные строки процессов | Только техническая телеметрия, минимум персональных данных |
| Не обновляет себя сам | Автообновление — тоже канал доставки исполняемого кода; агент обновляется MSI-пакетом через GPO/SCCM (9.6) |

### 1.3. Архитектурные принципы

1. **Односторонняя телеметрия.** Агент только отправляет данные. Ответы сервера содержат декларативную конфигурацию сбора из фиксированного набора полей (интервалы, флаг «прислать инвентаризацию»). Кода, который исполняет что-либо по указанию сервера, в агенте нет.
2. **Прозрачность.** Агент — обычная служба с понятным именем и описанием, виден в «Программах и компонентах», пишет в журнал событий Windows; состав собираемых данных задокументирован (1.4).
3. **Минимум инфраструктуры.** Один исполняемый файл сервера и PostgreSQL. Без брокера сообщений, Redis и внешнего веб-сервера.
4. **Данные агента — внешний ввод.** Валидация, лимиты размеров, вывод в UI только как текст.
5. **Сначала контракт.** OpenAPI и DDL — источник правды; серверные интерфейсы и TypeScript-типы генерируются из них.

### 1.4. Какие данные собираются

Перечень для согласования со службой ИБ и, при необходимости, для локального нормативного акта об ИТ-мониторинге.

| Категория | Данные | Персональные данные |
|---|---|---|
| Идентификация ПК | hostname, домен или рабочая группа, MachineGuid, SMBIOS UUID, серийный номер | нет (данные оборудования) |
| ОС | редакция, версия и сборка, разрядность, дата установки, время загрузки | нет |
| Оборудование | модель ПК, BIOS, CPU, модули RAM, диски, тома | нет |
| Сеть | MAC, IP-адреса и маски, шлюзы, DNS, DHCP, скорость адаптера | IP и MAC — идентификаторы устройства |
| ПО | название, версия, издатель, дата установки, разрядность; признак «установлено в профиль пользователя» — без SID и имени | нет |
| Метрики | загрузка CPU, RAM, свободное место | нет |
| Пользователь | имя пользователя активной сессии — **выключено по умолчанию** (`collect_logged_on_user`) | да — включать только по решению организации |

### 2.2. Компоненты

| Компонент | Ответственность | Технология |
|---|---|---|
| Агент `InvMonAgent` | сбор метрик и инвентаризации, локальный буфер, отправка | Go, служба Windows, MSI |
| Agent API | регистрация агентов, приём метрик и снимков инвентаризации, выдача конфигурации | Go, порт 8443 |
| Ingest | валидация, коррекция времени, пакетная запись, «горячее» состояние устройства | Go + pgx |
| Inventory | нормализация ПО, сравнение снимков, журнал изменений | Go |
| Web API + SPA | интерфейс администратора и REST для него | Go + React, порт 443 |
| Auth / RBAC / Audit | пароли, сессии, роли, журнал аудита | Go, argon2id |
| Jobs | вычисление алертов, доставка уведомлений, агрегация, хранение, партиции | River — очередь задач в PostgreSQL |
| PostgreSQL | всё состояние системы, включая очередь задач | PostgreSQL 17/18 |

Сервер — **модульный монолит**: один процесс, внутри — пакеты с явными границами (5.1). На масштабе 100–5 000 ПК микросервисы добавили бы только эксплуатационную сложность.

### 2.3. Потоки данных

**Регистрация агента** (один раз после установки):

```
Агент                                        Сервер                               БД
 │ POST /api/agent/v1/enroll                   │                                   │
 │ Authorization: Bearer imenr_…               │                                   │
 │ {agent_uid, hostname, os, hardware_ids} ───►│ токен регистрации: срок, отзыв,   │
 │                                             │ число использований, rate limit   │
 │                                             │ upsert devices по agent_uid ─────►│
 │                                             │ выпуск imagt_… (256 бит),         │
 │                                             │ в БД — только SHA-256 ───────────►│
 │                                             │ аудит agent.enroll ──────────────►│
 │◄─────────── 201 {device_id, device_token, config}                               │
 │ токен → DPAPI (LocalMachine); enroll_token удаляется из agent.yaml              │
```

**Метрики** (раз в 60 с): агент снимает CPU каждые 15 с и за минуту считает среднее и максимум, RAM — раз в минуту, тома — раз в 5 минут. Пачка попадает в локальный буфер и уходит `POST /api/agent/v1/metrics`. Сервер в одной транзакции корректирует время, пишет выборки в партиционированные таблицы (`ON CONFLICT DO NOTHING`), обновляет `device_state` и `device_volumes` и отвечает `config_version`, `inventory_requested`, `rotate_token`. Этот же запрос служит heartbeat.

**Инвентаризация**: раз в час агент собирает снимок и считает хэш канонического JSON (без изменчивых полей вроде свободного места). `PUT /api/agent/v1/inventory` — при старте, при изменении хэша и не реже раза в сутки. Сервер сравнивает снимок со своим состоянием, обновляет таблицы и пишет `inventory_changes`.

**Алерты**: задача раз в минуту выбирает нарушителей по каждому правилу, открывает алерты и **в той же транзакции** ставит уведомления в очередь (transactional outbox), закрывает алерты с учётом гистерезиса, повторяет уведомления по неподтверждённым. Доставка SMTP/webhook — отдельными задачами с повторами.

## 3. Технологический стек

### 3.1. Итог

| Слой | Выбор |
|---|---|
| Агент | **Go**. Сборка для Windows 10/11 — актуальным официальным тулчейном (1.27); для Windows 7/8.1 — форком [go-legacy-win7](https://github.com/thongtech/go-legacy-win7) той же версии (3.2) |
| Сервер | **Go**: `net/http` + chi, pgx v5, sqlc, goose (миграции), River (фоновые задачи), oapi-codegen, `log/slog`, go-mail |
| БД | **PostgreSQL 17/18**; расширения `pg_trgm` и `citext` из стандартной поставки |
| Очереди | **Отдельного брокера нет**: River (очередь задач в PostgreSQL) + transactional outbox; буфер при недоступности сервера — на стороне агента (3.3) |
| Frontend | **React + TypeScript + Vite**; Mantine (компоненты), TanStack Query и TanStack Table, Apache ECharts; типы API — `openapi-typescript` |
| Контракт | OpenAPI 3.1, contract-first |
| Упаковка | агент — MSI (WiX) для x86, x64, arm64; сервер — ZIP и `invmon-server.exe service install`, MSI после MVP |
| Подпись кода | сертификат подписи кода организации (AD CS) или коммерческий; `signtool` / `osslsigncode` |
| Тесты | `go test` + testcontainers (PostgreSQL), fuzz-тесты парсеров, Playwright (UI), симулятор агентов для нагрузки |

### 3.2. Почему Go — и для агента, и для сервера

- **Агент — один статический exe (~8–10 МБ) без рантаймов.** Не нужны .NET Framework и VC++ Redistributable — меньше предпосылок на старых ПК.
- **Собственный TLS-стек.** На Windows 7 TLS 1.2 в WinHTTP и .NET по умолчанию не используется (нужны KB3140245 и правка реестра), TLS 1.3 недоступен совсем. Go-агент работает через `crypto/tls` по TLS 1.2/1.3 на любом ПК, независимо от настроек SChannel.
- **Windows API из коробки:** `golang.org/x/sys/windows` — службы, журнал событий, реестр, DPAPI; WMI через COM — `github.com/yusufpapurcu/wmi`.
- **Сервер — тоже один exe**, SPA встроена в него (`go:embed`). Служба Windows без Python, Node или .NET на сервере; установка и обновление — замена файла. Тот же код собирается под Linux.
- **Общий код протокола** (типы из OpenAPI) у агента и сервера; все сборки кросс-компилируются в одном CI на Linux.
- **Запас по производительности:** 100 агентов — около двух запросов в секунду; один процесс Go с PostgreSQL выдерживает на порядки больше.

**Windows 7/8.1.** Официальный Go поддерживает Windows 7/8/8.1 только до версии 1.20: начиная с 1.21 нужен Windows 10 или Server 2016, а 1.20 уже не получает исправлений безопасности. Поэтому сборка для старых ОС делается форком `go-legacy-win7`: он повторяет официальные релизы (в сентябре 2026 — 1.27.1) и возвращает поддержку Windows 7/8/8.1 и Server 2008 R2/2012 R2. Форк изолирован в legacy-сегменте: ПК с Windows 10/11 получают сборку официальным тулчейном, а когда Win7/8.1 уйдут из парка, legacy-сборка просто удаляется. Версия форка закрепляется вместе с контрольными суммами; проверка на Win7 — первый пункт плана (этап 0).

### 3.3. Почему без брокера очередей

- **Нагрузка MVP:** 100 ПК × 1 запрос в минуту ≈ 1,7 запроса/с, инвентаризация — десятки снимков в час. У PostgreSQL запас в сотни раз, а брокер добавил бы ещё один сервис для установки, обновления, мониторинга и резервного копирования.
- **Там, где очередь нужна, она есть — в PostgreSQL.** River даёт `SKIP LOCKED`, повторы с увеличением задержки, периодические и уникальные задачи. Главное — задача ставится **в той же транзакции**, что и изменение данных: «алерт открыт» и «уведомление в очереди» атомарны, без потерь и дублей при падении процесса.
- **Буфер на время недоступности сервера — у агента** (локальный спул), поэтому приём метрик синхронный и простой.
- **Отвергнуто:** Redis — нет официальной сборки для Windows; RabbitMQ — отдельный Erlang-рантайм и эксплуатация ради пары сообщений в секунду.
- **Точка роста:** больше 5–10 тыс. агентов или несколько узлов приёма — NATS JetStream между Agent API и записью в БД (один бинарник, работает службой Windows).

### 3.4. Отвергнутые альтернативы

| Вариант | Почему нет |
|---|---|
| Python (FastAPI, Django) | рантайм и venv на сервере, службы через NSSM или pywin32; агент на Python для Win7 — только Python 3.8, давно без поддержки |
| Node.js (NestJS) | рантайм на сервере без выигрыша; агент на Node нереалистичен |
| C# / .NET | сильный вариант для Windows-команды, но современный .NET (8/10) не поддерживает Win7/8.1, а агент на .NET Framework 4.8 зависит от установленного фреймворка и SChannel (TLS 1.2 на Win7 — только после обновлений и правки реестра) |
| Rust | меньше размер и потребление, но медленнее разработка; цели сборки для Win7 — tier 3 (без гарантий стабильности) |
| TimescaleDB | полезен на тысячах ПК (сжатие, непрерывные агрегаты); для 100 ПК хватает встроенного партиционирования. Перейти можно позже без изменения API |
| Микросервисы | эксплуатационная сложность без выгоды на таком масштабе |

## 4. Агент

### 4.1. Процессная модель и бюджет ресурсов

- Служба `InvMonAgent`, запуск «Автоматически (отложенный запуск)», учётная запись **LocalSystem**. Она нужна, чтобы читать ПО из профилей всех вошедших пользователей (`HKU\<SID>`) и часть классов WMI. Риск компенсируется тем, что агент не принимает команд и не слушает порты (1.2), а его файлы защищены ACL (4.5). Если политика ИБ требует иного — режим `NT SERVICE\InvMonAgent` без ПО из пользовательских профилей.
- Восстановление службы: перезапуск через 1 мин, 1 мин, 5 мин; сброс счётчика через сутки. Внутренний watchdog: если основной цикл завис дольше 5 минут, процесс завершается, и диспетчер служб его перезапускает.
- Пониженный приоритет (`BELOW_NORMAL_PRIORITY_CLASS`), `GOMAXPROCS=2`, `GOMEMLIMIT=48MiB`.
- Целевой бюджет: **RAM ≤ 30 МБ, CPU ≤ 0,5 % в среднем, трафик ≈ 1,5–2 МБ в сутки** (одно keep-alive TLS-соединение, gzip).

### 4.2. Что и как собирается

**Метрики**

| Данные | Источник | Период |
|---|---|---|
| CPU, %: среднее и максимум за минуту | `GetSystemTimes` — разница счётчиков idle/kernel/user; выборка каждые 15 с | отправка раз в 60 с |
| RAM: всего и занято | `GlobalMemoryStatusEx` | 60 с |
| Тома: размер и свободное место | `GetLogicalDriveStringsW` + `GetDriveTypeW` (только `DRIVE_FIXED`) + `GetDiskFreeSpaceExW` | 300 с |
| Время загрузки | `GetTickCount64` | 60 с |

Счётчики производительности (PDH) по именам не используются: в русской Windows они локализованы («\Процессор(_Total)\% загруженности процессора»). Если понадобятся — только через `PdhAddEnglishCounter`.

**Инвентаризация**: сбор при старте, затем раз в 60 минут; отправка — если изменился хэш, полный снимок — раз в сутки.

| Данные | Источник |
|---|---|
| ОС | `Win32_OperatingSystem`; реестр `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion` (`DisplayVersion`/`ReleaseId`, `UBR`) |
| Модель, производитель, BIOS, идентификаторы | `Win32_ComputerSystem`, `Win32_ComputerSystemProduct` (UUID), `Win32_BIOS`; `MachineGuid` из `HKLM\SOFTWARE\Microsoft\Cryptography` |
| CPU | `Win32_Processor`: Name, NumberOfCores, NumberOfLogicalProcessors, MaxClockSpeed |
| Модули RAM | `Win32_PhysicalMemory`: Capacity, Speed, Manufacturer, PartNumber, DeviceLocator |
| Физические диски | `Win32_DiskDrive`; на Windows 8+ дополнительно `MSFT_PhysicalDisk` (`root\Microsoft\Windows\Storage`) — тип SSD/HDD и шина NVMe/SATA |
| Сетевые адаптеры | `Win32_NetworkAdapter` (физические) + `Win32_NetworkAdapterConfiguration` (IPEnabled): MAC, IP и маски, шлюзы, DNS, DHCP, скорость |
| Установленное ПО | реестр `…\CurrentVersion\Uninstall`: HKLM в 64- и 32-битном представлении (`KEY_WOW64_64KEY` / `KEY_WOW64_32KEY`) и загруженные кусты `HKU\<SID>` |
| Пользователь активной сессии | `WTSGetActiveConsoleSessionId` + `WTSQuerySessionInformation` — только при `collect_logged_on_user = true` |

Правила сбора ПО:

- **`Win32_Product` не используется.** Запрос к этому классу запускает проверку согласованности всех MSI-пакетов: возможны «самовосстановления» продуктов, события 1035 в журнале и десятки секунд работы.
- Отбрасываются записи без `DisplayName`, с `SystemComponent = 1`, с `ParentKeyName` или с `ReleaseType` из {Update, Hotfix, Security Update, ServicePack}: это обновления и компоненты, а не продукты.
- Если имя ключа — GUID и `WindowsInstaller = 1`, оно передаётся как `msi_product_code`.
- Профили невошедших пользователей не загружаются (чужие `NTUSER.DAT` не трогаем); для установок в профиль передаётся только `scope: "user"` — без SID и имени.

### 4.3. Особенности Windows 7/8.1

- **Отдельная сборка** (форк Go, 3.2). MSI содержит обе сборки и выбирает нужную по версии ОС. Признак Windows 10+ — наличие `CurrentMajorVersionNumber` в `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion`. Свойство MSI `VersionNT` для этого не годится: на Windows 10 оно равно 603, как на 8.1.
- **TLS не зависит от ОС.** Агент сам реализует TLS 1.2/1.3 и доверяет только CA из своей конфигурации, а не устаревшему хранилищу сертификатов Win7.
- На Win7 нет `MSFT_PhysicalDisk` — тип носителя `Unknown`; нет `DisplayVersion` — передаётся «SP1».
- Windows 11 определяется по номеру сборки ≥ 22000: `ProductName` в реестре у неё по-прежнему «Windows 10 …». Название ОС берётся из `Win32_OperatingSystem.Caption`.
- **WMI на старых ПК бывает повреждён.** Каждый WMI-запрос выполняется с таймаутом 30 с (COM инициализируется на закреплённом потоке ОС). Ошибка не роняет агента: она попадает в `errors[]`, и снимок отправляется частичным. В UI — пометка и ссылка на инструкцию (`winmgmt /verifyrepository`).

### 4.4. Надёжность

- **Локальный буфер** (`bbolt`, файл `spool.db`): пачки, которые не удалось доставить. Лимит — 24 часа или 20 МБ, старые вытесняются. После восстановления связи — досылка частями до 1000 выборок, от старых к новым.
- **Повторы** — экспоненциальная задержка со случайным разбросом (5 с → 10 мин) и соблюдением `Retry-After` на 429/503. После перезапуска сервера агенты не приходят одновременно.
- **Идемпотентность.** Ключ выборки — (устройство, время[, том]): повтор пачки после потерянного ответа не создаёт дублей. Регистрация идемпотентна по `agent_uid`.
- **Время.** Агент передаёт `sent_at`; сервер оценивает расхождение часов и при |Δ| > 2 мин сдвигает метки выборок, а в карточке ПК показывает предупреждение. Актуально для ПК в рабочих группах без синхронизации с контроллером домена.
- **Реакция на ответы сервера:** 401 — пауза 1 ч и повтор, запись в журнал событий; 403 `pending_approval` — повтор раз в 5 минут; 403 `device_revoked` — отправка прекращается (проверка раз в сутки) до переустановки.

| Путь | Содержимое | Доступ |
|---|---|---|

TLS-клиент агента доверяет только своему CA и может закрепить ключ сервера:

```go
func agentTLSConfig(caPEM []byte, serverName string, pins [][]byte) (*tls.Config, error) {
	pool := x509.NewCertPool()
	if !pool.AppendCertsFromPEM(caPEM) {
		return nil, errors.New("ca_file: сертификаты не найдены")
	}
	cfg := &tls.Config{
		MinVersion: tls.VersionTLS12,
		RootCAs:    pool, // не системное хранилище: на Win7 оно устаревшее, а подменить его проще
		ServerName: serverName,
	}
	if len(pins) > 0 {
		cfg.VerifyConnection = func(cs tls.ConnectionState) error {
			for _, chain := range cs.VerifiedChains {
				for _, cert := range chain {
					sum := sha256.Sum256(cert.RawSubjectPublicKeyInfo)
					for _, pin := range pins {
						if bytes.Equal(sum[:], pin) {
							return nil
						}
					}
				}
			}
			return errors.New("ключ сервера не совпадает с закреплённым (pin_sha256)")
		}
	}
	return cfg, nil
}
```

Раздельные порты позволяют закрыть веб-интерфейс от пользовательских сегментов, не мешая агентам. На обоих — TLS 1.2/1.3 и жёсткие таймауты:

```go
func newAgentServer(handler http.Handler) *http.Server {
	return &http.Server{
		Addr:    ":8443",
		Handler: handler,
		TLSConfig: &tls.Config{
			MinVersion: tls.VersionTLS12,
			// Список применяется только к TLS 1.2; для TLS 1.3 Go использует свой безопасный набор.
			CipherSuites: []uint16{
				tls.TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256,
				tls.TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,
				tls.TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384,
				tls.TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384,
				tls.TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305_SHA256,
				tls.TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256,
			},
		},
		ReadHeaderTimeout: 10 * time.Second,
		ReadTimeout:       60 * time.Second,
		IdleTimeout:       150 * time.Second, // > интервала отправки: агент держит одно TLS-соединение
		MaxHeaderBytes:    16 << 10,
	}

```

`IdleTimeout` больше интервала отправки, поэтому агент не проходит полный TLS-handshake каждую минуту.

### 5.3. Приём метрик

1. **Аутентификация:** SHA-256 от Bearer-токена ищется в `devices.token_hash` (или в `prev_token_hash`, пока не истёк срок перекрытия). Статус `pending` или `revoked` → 403.
2. **Лимиты:** тело ≤ 1 МБ **после распаковки gzip** (защита от gzip-бомб), ≤ 1000 выборок, 60 запросов в минуту на устройство.
3. **Валидация:** CPU от 0 до 100, `mem_used ≤ mem_total`, `free ≤ total`, том по шаблону `^[A-Z]:$`; выборки не старше 14 дней и не из будущего (больше 5 минут после коррекции).
4. **Одна транзакция:** пакетная вставка через `unnest` с `ON CONFLICT DO NOTHING`, обновление `device_state` и `device_volumes`.
5. **Ответ:** `config_version`, `inventory_requested`, `rotate_token`.

```sql
-- $1 — device_id; $2…$6 — массивы значений одной пачки агента
INSERT INTO metrics_host (device_id, ts, cpu_pct, cpu_max_pct, mem_used_bytes, mem_total_bytes)
SELECT $1, t.ts, t.cpu, t.cpu_max, t.mem_used, t.mem_total
FROM unnest($2::timestamptz[], $3::real[], $4::real[], $5::bigint[], $6::bigint[])
     AS t(ts, cpu, cpu_max, mem_used, mem_total)
ON CONFLICT (device_id, ts) DO NOTHING;
```

IP-адрес устройства берётся из TCP-соединения; `X-Forwarded-For` учитывается только от доверенных обратных прокси, если они есть.

### 5.4. Инвентаризация: нормализация и сравнение

Нормализация ПО — чтобы «7-Zip 23.01 (x64)» и «7-Zip 24.08 (x64)» были одним продуктом с разными версиями:

- из `DisplayName` убираются версия (если совпадает с `DisplayVersion`) и пометки разрядности и локали: `(x64)`, `(64-bit)`, `(x86)`, `(32-bit)`, `x64 ru`;
- издатель — через словарь синонимов: «Microsoft Corporation» → «Microsoft», «Google LLC» → «Google»;
- `version_parts` — первые четыре числовые части версии (`"129.0.6668.90"` → `{129,0,6668,90}`), чтобы сравнивать версии в SQL;
- исходный `DisplayName` сохраняется всегда.

Сравнение снимка с текущим состоянием, в одной транзакции:

- **ПО:** ключ — (продукт, версия, разрядность, scope). Исчезнувшие записи закрываются (`removed_at`), новые добавляются; смена версии — это закрытие старой записи и добавление новой. История установок получается без отдельной таблицы.
- **Железо, диски, тома, адаптеры:** по естественным ключам — серийный номер диска, буква тома, MAC.
- Каждое отличие → строка `inventory_changes` (added / removed / changed, старое и новое значение).
- В хэш снимка не входят изменчивые поля — свободное место, время загрузки, `collected_at`, иначе снимок уходил бы каждый час.

**Дубли устройств.** Образ, клонированный без sysprep, даёт одинаковый `MachineGuid`, а иногда и SMBIOS UUID. Поэтому идентичность устройства — `agent_uid`, который генерируется при установке агента. Аппаратные идентификаторы служат только подсказками: «похоже на ранее выведенное устройство X» (переустановка ОС) или «у двух активных устройств одинаковый MachineGuid» (клон). Объединение записей — вручную в UI.

### 5.5. Движок алертов

Правило: метрика (`cpu_pct`, `mem_used_pct`, `disk_free_pct`, `disk_free_bytes`, `offline`), оператор и порог, окно `duration`, порог закрытия `resolve_threshold` (гистерезис), область действия (все устройства, группа или тег), для дисков — том (`C:` или `*`), каналы и интервал повторных уведомлений.

Семантика:

- **Окно.** Условие должно выполняться на всём окне: для `>` берётся минимум за окно, для `<` — максимум. Окно должно быть покрыто данными минимум на 80 %. `duration = 0` — проверка по последнему значению.
- **Offline** — нет данных дольше `duration`. Остальные правила по «молчащему» устройству не вычисляются и не закрываются: нет данных — нет решения.
- **Дедупликация:** не больше одного активного алерта на (правило, устройство, том) — это гарантирует частичный уникальный индекс.
- **Гистерезис:** алерт «свободно < 10 %» закрывается только при ≥ 12 %, без «дребезга» уведомлений.
- **Уведомления:** при открытии, при закрытии и повторно раз в `renotify_interval`, пока алерт активен и не подтверждён.
- **Правила «из коробки»:** свободно на C: < 10 % (critical), на любом томе < 15 % (warning), CPU > 90 % 15 минут, RAM > 90 % 15 минут, нет связи 10 минут.

Цикл вычисления — задача River раз в 60 секунд. Она уникальна: при нескольких экземплярах сервера выполняется один раз.

```sql
-- Нарушители правила с окном: CPU > 90 % все 15 минут
SELECT r.id AS rule_id, m.device_id, '' AS dimension,
       CASE WHEN r.operator IN ('>', '>=') THEN min(m.cpu_pct) ELSE max(m.cpu_pct) END AS value
FROM alert_rules r
JOIN devices d      ON d.status = 'active'
                   AND (r.scope_group_id IS NULL OR d.group_id = r.scope_group_id)
                   AND (r.scope_tag IS NULL OR r.scope_tag = ANY (d.tags))
JOIN metrics_host m ON m.device_id = d.id
                   AND m.ts > now() - r.duration AND m.ts <= now()  -- диапазон с двух сторон → отсечение партиций
WHERE r.enabled AND r.metric = 'cpu_pct'
GROUP BY r.id, m.device_id
HAVING count(*) >= 0.8 * extract(epoch FROM r.duration) / 60        -- окно покрыто данными ≥ 80 % (интервал 60 с)
   AND alert_cmp(CASE WHEN r.operator IN ('>', '>=') THEN min(m.cpu_pct) ELSE max(m.cpu_pct) END,
                 r.operator, r.threshold);

-- Открытие алерта: повторный цикл не создаёт дубль
INSERT INTO alerts (rule_id, device_id, dimension, severity, value, last_value, message)
VALUES ($1, $2, $3, $4, $5, $5, $6)
ON CONFLICT (rule_id, device_id, dimension) WHERE state = 'firing' DO NOTHING
RETURNING id;

-- Закрытие с гистерезисом (дисковое правило)
UPDATE alerts a
SET state = 'resolved', resolved_at = now(), last_value = v.free_pct
FROM alert_rules r, device_volumes v
WHERE a.rule_id = r.id AND r.id = $1 AND a.state = 'firing'
  AND v.device_id = a.device_id AND v.volume = a.dimension
  AND NOT alert_cmp(v.free_pct, r.operator, COALESCE(r.resolve_threshold, r.threshold))
RETURNING a.id;
```

Для каждого нового алерта в той же транзакции создаются записи `notification_log` и задачи доставки River.

### 5.6. Уведомления

- Каналы MVP: **email** (почтовый релей организации, STARTTLS, при необходимости SMTP AUTH) и **webhook** (универсальный JSON). Мессенджеры — Telegram, Mattermost, Teams — появятся в v1.1 как готовые шаблоны webhook.

Проверка подписи на стороне получателя:

```python
import hashlib
import hmac
import time


def verify_invmon_signature(secret: bytes, header: str, body: bytes, max_age_s: int = 300) -> bool:
    """Проверка заголовка X-InvMon-Signature: t=<unix>,v1=<hex>."""
    try:
        parts = dict(item.split("=", 1) for item in header.split(","))
        ts, signature = int(parts["t"]), parts["v1"]
    except (KeyError, ValueError):
        return False
    if abs(time.time() - ts) > max_age_s:  # защита от повторной отправки старого сообщения
        return False
    expected = hmac.new(secret, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)
```

### 5.7. Фоновые задачи

| Задача | Расписание | Что делает |
|---|---|---|
| `evaluate_alerts` | раз в 60 с | правила → открытие, закрытие, повторы; постановка уведомлений |
| `deliver_notification` | по событию | отправка SMTP и webhook с повторами |
| `rollup_hourly` | ежечасно (в :05) | часовые агрегаты `metrics_*_hourly` за прошедший час |
| `partitions` | раз в сутки | `ensure_partitions` на 8 дней вперёд, `drop_partitions_older_than` по сроку хранения |
| `retention` | раз в сутки | удаление закрытых алертов старше 180 дней, удалённого ПО старше 365 дней, истёкших сессий, метрик удалённых устройств |
| `stale_devices` | раз в сутки | список ПК, не выходивших на связь дольше 30 дней |

### 5.8. Веб-интерфейс

| Экран | Содержимое |
|---|---|
| Сводка | онлайн и офлайн, активные алерты по важности, где меньше всего места, ПК без связи дольше 7 дней, устаревшие версии агента, распределение ОС |

## 6. База данных

Полный DDL — [`db/schema.sql`](db/schema.sql), проверка — [`db/verify.sql`](db/verify.sql).

### 6.1. Обзор

```
device_groups ─┬─< devices >── enrollment_tokens
               │     ├── device_state        1:1, «горячее» состояние (обновляется каждую минуту)
               │     ├── device_hardware     1:1, железо + исходный JSON
               │     ├─< device_disks, device_volumes, device_network_adapters
               │     ├─< device_software >── software      история: first_seen_at / removed_at
               │     ├─< inventory_changes
               │     └─< alerts >── alert_rules >─< alert_rule_channels >── notification_channels
               └──────────────────── alert_rules.scope_group_id

metrics_host, metrics_disk                 партиции по суткам, 14 дней; без FK ради скорости вставки
metrics_host_hourly, metrics_disk_hourly   часовые агрегаты, ~13 месяцев
users ─< sessions      audit_log (партиции по месяцам, только INSERT)      settings      notification_log
```

### 6.2. Ключевые таблицы

| Таблица | Назначение | Решения |
|---|---|---|
| `devices` | реестр устройств | `agent_uid` — идентичность; `token_hash` и `prev_token_hash` — ротация токена без простоя; статусы pending / active / revoked / retired |
| `device_state` | последние значения для списка и алертов | отдельная таблица с `fillfactor = 70`: HOT-обновления каждую минуту не раздувают `devices` |
| `device_volumes` | тома и текущее свободное место | `free_pct` — вычисляемая колонка |
| `software`, `device_software` | каталог и установленное ПО | справочник (название, издатель); `version_parts int[]` для сравнения версий; частичный уникальный индекс по «живым» строкам |
| `metrics_host`, `metrics_disk` | сырые метрики | `PARTITION BY RANGE (ts)`; первичный ключ (устройство, время) — идемпотентная вставка; BRIN по `ts` |
| `metrics_*_hourly` | агрегаты | среднее и максимум CPU и RAM, минимум свободного места |
| `alert_rules`, `alerts` | правила и их срабатывания | CHECK на согласованность полей правила; частичный уникальный индекс на активный алерт |
| `notification_log` | журнал доставки | outbox: пишется в одной транзакции с алертом |
| `audit_log` | аудит | партиции по месяцам; UPDATE и DELETE запрещены правами и триггером |
| `settings` | настройки | JSONB по ключам: `agent`, `retention`, `smtp` и т. д. |

### 6.3. Метрики: партиции, агрегаты, хранение

- Сырые данные — партиции по суткам (UTC). Создание на 8 дней вперёд и удаление старых — функции `ensure_partitions` и `drop_partitions_older_than`. Они `SECURITY DEFINER` с белым списком таблиц: рабочая роль управляет партициями, не владея таблицами. Удаление партиции мгновенное, без `DELETE` и раздувания таблиц.
- Сроки хранения по умолчанию: сырые метрики — 14 дней, часовые агрегаты — 400 дней, аудит — 13 месяцев. Функция не даст удалить аудит младше 12 месяцев, даже если приложение попросит.
- Графики: до 48 часов — сырые точки; до 14 дней — корзины по 15 минут (`date_bin`); дольше — часовые агрегаты.
- Запросы к метрикам всегда ограничивают `ts` **с двух сторон**: при одностороннем условии планировщик не отбрасывает будущие (пустые) партиции.
- Собственные функции вместо `pg_partman` — чтобы не зависеть от расширений вне стандартной поставки PostgreSQL для Windows.

### 6.4. Объёмы

Замер на PostgreSQL 16, сутки данных для 100 ПК: `metrics_host` — 144 000 строк, 15 МБ (около 109 байт на строку вместе с индексами); `metrics_disk` (в среднем 1,5 тома на ПК, раз в 5 минут) — 43 200 строк, 5,6 МБ.

| Парк | Сырые метрики за 14 дней | Агрегаты за год | Диск через год* |
|---|---|---|---|
| 100 ПК | ≈ 0,3 ГБ | ≈ 0,25 ГБ | ≈ 2 ГБ |
| 1 000 ПК | ≈ 3 ГБ | ≈ 2,5 ГБ | ≈ 8 ГБ |
| 5 000 ПК | ≈ 15 ГБ | ≈ 12 ГБ | ≈ 35 ГБ |

\* вместе с инвентаризацией, аудитом, WAL (до 1 ГБ при настройках по умолчанию) и запасом на VACUUM.

### 6.5. Роли и права

- `invmon_owner` — владелец схемы. Под ним применяются миграции (goose при старте сервера, под advisory-lock); для рабочих запросов не используется.
- `invmon_app` — рабочая роль сервера: `SELECT/INSERT/UPDATE/DELETE`, на `audit_log` — только `SELECT/INSERT`; партиции — только через `SECURITY DEFINER`-функции.
- `verify.sql` проверяет: под рабочей ролью `UPDATE`, `DELETE` и `TRUNCATE` журнала аудита отклоняются правами, под владельцем `UPDATE` и `DELETE` — триггером; создать партицию напрямую рабочая роль не может.
- Настоящая неизменяемость аудита — копия во внешнем SIEM или syslog (v1.1).

Полный контракт — [`api/openapi.yaml`](api/openapi.yaml).

### 7.1. Соглашения

- REST и JSON в UTF-8; время — RFC 3339 в UTC; размеры — в байтах (int64); проценты — от 0 до 100.
- Версия — в пути: `/api/agent/v1`, `/api/v1`. Несовместимые изменения — только новой версией пути; предыдущую версию Agent API сервер поддерживает минимум два релиза, потому что агенты обновляются волнами.

## 8. Безопасность и журналирование

### 8.1. TLS

- Только TLS 1.2 и 1.3; для 1.2 — только ECDHE с AEAD-шифрами (AES-GCM, ChaCha20-Poly1305): без обмена ключами RSA, без CBC и SHA-1. HSTS на веб-интерфейсе.
- Сертификат сервера предпочтительно выпускает корпоративный CA (AD CS). Если его нет, `invmon-server.exe gen-certs` создаёт собственный CA (ECDSA P-256, 10 лет) и сертификат сервера (2 года, SAN — DNS-имя и IP); закрытый ключ CA хранится офлайн.
- Агент проверяет цепочку **только по CA из своей конфигурации** и имя сервера; опционально — пиннинг ключа. Замену сертификата сервера, выпущенного тем же CA, агенты не замечают.
- Приёмка релиза: `nmap --script ssl-enum-ciphers -p 443,8443` или `testssl.sh`.

### 8.2. Токены агентов

| | Токен регистрации `imenr_…` | Токен устройства `imagt_…` |
|---|---|---|
| Кто выпускает | администратор в UI | сервер при регистрации |
| Энтропия | 256 бит | 256 бит |
| Хранение на сервере | SHA-256 | SHA-256: быстрого хэша достаточно, перебрать 2²⁵⁶ невозможно (argon2 нужен для паролей, а не для случайных токенов) |
| Хранение на ПК | только до регистрации, затем удаляется из `agent.yaml` | DPAPI LocalMachine + ACL |
| Ограничения | срок (до 365 дней, по умолчанию 30), число использований, группа по умолчанию, режим одобрения, лимит запросов с IP | привязан к одному устройству; лимит запросов; ротация раз в 90 дней с перекрытием 24 часа |
| Отзыв | кнопка в UI; уже зарегистрированные агенты продолжают работу | «Отозвать» в карточке ПК → 403 `device_revoked` |

Префиксы `imenr_` и `imagt_` помогают сканерам секретов находить токены в репозиториях и журналах. В журналы токены не пишутся, в UI показывается только префикс.

**Утечка токена регистрации.** При раздаче через GPO токен лежит в SYSVOL или на общем ресурсе, который читают все пользователи домена. Меры: короткий срок и лимит использований на каждую волну развёртывания, режим «новые устройства требуют одобрения», аудит регистраций (hostname, IP), отзыв токена после волны. Худший сценарий — поддельное «устройство» с ложной телеметрией: команд оно не получит и чужих данных не увидит.

### 8.3. Пользователи, роли, сессии

- **Локальные пользователи.** Пароли — argon2id (m = 64 МиБ, t = 3, p = 2), не короче 12 символов, с проверкой по списку частых и утёкших паролей. Первый администратор создаётся командой `invmon-server.exe create-admin` (одноразовый пароль, смена при первом входе).
- **Роли:** admin — всё, включая пользователей, каналы, токены и удаление устройств; operator — правила алертов, подтверждение, группы и теги, одобрение устройств; viewer — только чтение. Роль для каждой операции указана в `x-required-role` в OpenAPI и проверяется в middleware; на каждую операцию есть тест.
- **Сессии:** 256-битный идентификатор в cookie `__Host-invmon_session` (Secure, HttpOnly, SameSite=Strict), в БД — только его хэш; тайм-аут бездействия 30 минут, максимум 12 часов. Выход и смена пароля завершают все сессии пользователя.
- **Перебор паролей:** после 10 неудачных попыток учётная запись блокируется на 15 минут, плюс лимит по IP; на «нет пользователя» и «неверный пароль» — одинаковый ответ.
- **Браузер:** CSRF закрывают SameSite=Strict и проверка `Origin` на изменяющих запросах. Заголовки: `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- **v1.1:** вход через LDAP/AD (LDAPS, сопоставление групп AD ролям) и TOTP.

### 8.4. Секреты на сервере

| Секрет | Где хранится |
|---|---|
| Пароли БД и SMTP | в `server.yaml`, значение зашифровано DPAPI (LocalMachine), префикс `dpapi:`; файл доступен только SYSTEM, администраторам и учётной записи службы |
| Секреты webhook | в БД, AES-256-GCM на мастер-ключе; через API не возвращаются (`writeOnly`) |
| Мастер-ключ | файл под DPAPI с ACL; резервная копия — в хранилище паролей организации: без неё зашифрованные секреты не восстановить |
| Закрытый ключ TLS | файл с ACL; ключ CA — офлайн |

Служба сервера работает от виртуальной учётной записи `NT SERVICE\InvMonServer`, а не от LocalSystem: ей нужны только свои папки и сетевые порты. В Windows привязка к порту 443 прав администратора не требует.

### 8.5. Журнал аудита

Событие пишется в `audit_log` в той же транзакции, что и само действие.

| Группа | События |
|---|---|
| Вход | `user.login` (успех или неудача, IP, User-Agent), `user.logout`, `user.locked`, `user.password_changed` |
| Пользователи | `user.create`, `user.update`, `user.disable`, `user.delete` — с изменением роли «было / стало» |
| Устройства | `device.approve`, `device.update`, `device.revoke`, `device.delete`, `device.merge`, `device.inventory_refresh` |
| Агенты | `agent.enroll` (успех или неудача: префикс токена, IP, hostname), `agent.token_rotate`, `agent.auth_failed` (агрегировано: не чаще одной записи в 10 минут на IP) |
| Алерты | `alert_rule.create/update/delete` (с diff), `alert.ack`, `channel.create/update/delete/test` |
| Администрирование | `enrollment_token.create/revoke`, `settings.update` (секреты вырезаны) |
| Данные | `report.export` — кто и что выгрузил |

Хранение — 13 месяцев, просмотр — только admin, отправка в SIEM (syslog RFC 5424 поверх TLS) — v1.1.

### 8.6. Технические журналы

- **Сервер:** JSON (`log/slog`) в `C:\ProgramData\InvMon\Server\logs\` с ротацией; ошибки дублируются в журнал событий Windows (источник `InvMonServer`). Каждому запросу присваивается `request_id`, он же возвращается в ответе об ошибке.
- **Агент:** см. 4.5.
- В журналы не попадают токены, пароли, cookie и тела запросов.

### 8.7. Модель угроз

| Угроза | Меры |
|---|---|
| Перехват или подмена трафика агент ↔ сервер | TLS 1.2+, проверка по собственному CA, опционально — пиннинг ключа |
| Поддельный агент, «отравление» данных | токены регистрации со сроком и лимитом, режим одобрения, лимиты запросов, предупреждения о дублях идентификаторов |
| Кража токена устройства | DPAPI + ACL, ротация, отзыв; ущерб ограничен телеметрией одного ПК |
| Компрометация сервера | канала управления ПК нет по замыслу; служба без прав администратора; отдельная роль БД; резервные копии |
| Stored XSS через данные инвентаризации (например, `DisplayName`) | проверка длины и формата на приёме, вывод только как текст, строгий CSP |
| Перебор паролей | argon2id, блокировки, лимиты по IP, UI доступен только из сети ИТ, TOTP (v1.1) |
| Локальное повышение привилегий через файлы агента | защищённый DACL на папке данных, бинарник в Program Files, путь службы в кавычках, подпись кода |
| DoS от агентов (ошибка или шторм) | лимиты тела с учётом gzip, лимит запросов на токен, `Retry-After`, случайный разброс задержек у агентов |
| Подделка журнала аудита | права и триггер, минимальный срок хранения в функции очистки, копия в SIEM (v1.1) |

## 9. Развёртывание и эксплуатация

### 9.1. Требования к серверу

| Парк | vCPU | RAM | SSD | Схема |
|---|---|---|---|---|
| до 100 ПК | 2 | 4 ГБ | 40 ГБ | сервер и PostgreSQL на одной ВМ |
| до 1 000 ПК | 4 | 8 ГБ | 100 ГБ | так же |
| до 5 000 ПК | 8 | 16 ГБ | 250 ГБ | PostgreSQL на отдельной ВМ |

Оценки уточняются нагрузочным тестом на этапе 4.

ОС: **Windows Server 2019, 2022 или 2025** (PostgreSQL 18 требует Windows 10 / Server 2016 и новее). Windows 10/11 — только для стенда и пилота: клиентская ОС не предназначена для серверной роли, а Windows 10 вне основной поддержки с 14.10.2025.

### 9.2. Установка сервера на Windows Server

1. **PostgreSQL 17/18** — официальный установщик для Windows. В `postgresql.conf`: `listen_addresses = 'localhost'` (если БД на том же сервере) и `password_encryption = scram-sha-256`; в `pg_hba.conf` — только `scram-sha-256`. Роли и БД:
   ```sql
   CREATE ROLE invmon_owner LOGIN PASSWORD '…';
   CREATE ROLE invmon_app   LOGIN PASSWORD '…';
   CREATE DATABASE invmon OWNER invmon_owner;
   ```
2. Распаковать `InvMonServer-<версия>-windows-x64.zip` в `C:\Program Files\InvMon\Server\`.
3. Инициализация — из PowerShell от имени администратора:
   ```powershell
   cd 'C:\Program Files\InvMon\Server'
   # Создаёт C:\ProgramData\InvMon\Server\{server.yaml, tls\, secrets\, logs\} с ACL,
   # запрашивает пароли БД и шифрует их DPAPI, применяет миграции, генерирует мастер-ключ,
   # а если корпоративного сертификата нет — собственный CA и сертификат сервера.
   .\invmon-server.exe init --public-url https://invmon.corp.local `
       --db-owner-url 'postgres://invmon_owner@localhost:5432/invmon' `
       --db-app-url   'postgres://invmon_app@localhost:5432/invmon'
   .\invmon-server.exe create-admin --username admin
   # Служба InvMonServer: NT SERVICE\InvMonServer, автозапуск, перезапуск при сбое
   .\invmon-server.exe service install
   Start-Service InvMonServer
   ```
4. Межсетевой экран:
   ```powershell
   New-NetFirewallRule -DisplayName 'InvMon Agents' -Direction Inbound -Protocol TCP -LocalPort 8443 `
       -RemoteAddress 192.168.0.0/16 -Action Allow
   New-NetFirewallRule -DisplayName 'InvMon Web UI' -Direction Inbound -Protocol TCP -LocalPort 443 `
       -RemoteAddress 10.10.0.0/24 -Action Allow
   ```
5. DNS-запись `invmon.corp.local`. Проверка: `https://invmon.corp.local/readyz`, вход в UI, «Отправить тест» для SMTP-канала.

Тот же сервер собирается и под Linux (systemd); готовый пакет и Docker-образ — после MVP.

### 9.3. Конфигурация сервера

```yaml
# C:\ProgramData\InvMon\Server\server.yaml
public_url: 'https://invmon.corp.local'
agent_listener:

  tls_key:  'C:\ProgramData\InvMon\Server\tls\server.key'

  app_password: 'dpapi:AQAAANCMnd8BFdERjHoAwE/Cl+sBAAAA…'
  owner_url: 'postgres://invmon_owner@localhost:5432/invmon?sslmode=disable'  # только для миграций
  owner_password: 'dpapi:AQAAANCMnd8BFdERjHoAwE/Cl+sBAAAA…'
```

### 9.4. Развёртывание агентов

Сборки: `InvMonAgent-<версия>-x64.msi`, `-x86.msi`, `-arm64.msi`. Установщик сам выбирает бинарник — обычный или legacy — по версии Windows.

```bat
msiexec /i InvMonAgent-1.0.0-x64.msi /qn /l*v "%TEMP%\invmon-agent.log" ^
    SERVER_URL=https://invmon.corp.local:8443 ^
    ENROLL_TOKEN=imenr_7Hk2… ^
    CA_FILE=\\corp.local\NETLOGON\invmon\ca.pem
```

| Способ | Как передать параметры | Комментарий |
|---|---|---|
| SCCM/MECM, PDQ Deploy, Kaspersky Security Center и т. п. | командная строка выше | предпочтительно: есть отчёт об установке |
| GPO → Software Installation (назначение компьютерам) | трансформация `.mst`: параметры командной строки GPO не передаёт | MSI — на ресурсе, доступном на чтение группе «Компьютеры домена» |
| GPO → сценарий автозагрузки компьютера | командная строка + проверка «уже установлено» | просто, но без отчётности |
| Вручную, ПК вне домена | командная строка или мастер установки | для рабочих групп |

Порядок раскатки: пилот (ИТ-отдел и 5–10 ПК разных поколений, включая Win7) → неделя наблюдения → волны по 30–50 % парка, у каждой волны свой токен регистрации.

Удаление: `msiexec /x {ProductCode} /qn` или через GPO; в UI устройство выводится из эксплуатации (данные сохраняются) или удаляется.

### 9.5. Резервное копирование и восстановление

- Ежесуточно — Планировщиком заданий, от учётной записи с доступом к БД через `pgpass.conf`:
  ```powershell
  $ts   = Get-Date -Format 'yyyyMMdd-HHmm'
  $dest = 'D:\Backup\InvMon'
  & 'C:\Program Files\PostgreSQL\18\bin\pg_dump.exe' -h localhost -U invmon_owner -Fc `
      -f "$dest\invmon-$ts.dump" invmon
  if ($LASTEXITCODE -ne 0) { throw "pg_dump failed: $LASTEXITCODE" }
  Get-ChildItem $dest -Filter 'invmon-*.dump' |
      Where-Object LastWriteTime -lt (Get-Date).AddDays(-14) | Remove-Item
  ```
  Копия уходит на сетевой ресурс или в систему резервного копирования организации.
- Отдельно и при каждом изменении: `server.yaml`, папка `tls\` и **мастер-ключ** — в защищённое хранилище.
- Для MVP: RPO — 24 часа, RTO — около часа. Если нужен меньший RPO — архивирование WAL (`archive_command`) и `pg_basebackup` (v1.1).
- Восстановление: `pg_restore --clean --if-exists -d invmon <файл>`, затем запуск службы. Проверочное восстановление на стенде — раз в квартал.
- Метрики за время простоя сервера не теряются: агенты досылают буфер (до 24 часов).

### 9.6. Обновления

- **Сервер:** резервная копия → остановка службы → замена файлов → запуск. Миграции применяются при старте автоматически (goose, под advisory-lock, каждая в своей транзакции). Откат — восстановление копии и предыдущих бинарников: миграции только вперёд.
- **Агенты:** новая версия MSI (`MajorUpgrade`) тем же способом, что и установка. UI показывает версии агентов и устаревшие. Сервер принимает агентов текущей и предыдущей версии API.
- **Автообновления агентов нет** (1.2). Если оно понадобится — только пакеты, подписанные ключом организации, с проверкой подписи агентом и включением через политику.

### 9.7. Мониторинг самой системы

- `/readyz` — для внешнего мониторинга (Zabbix, Uptime Kuma и т. п.).
- `/metrics` в формате Prometheus (доступ по списку IP): скорость приёма, ошибки валидации, длительность цикла алертов, очередь и ошибки доставки уведомлений.
- Встроенная проверка «тишины»: если за 10 минут не пришло данных ни от одного агента — письмо администраторам.
- Ошибки сервера — в журнале событий Windows.

## 10. План разработки MVP

### 10.1. Команда и сроки

Три разработчика — Go backend, Go-агент и Windows, frontend — плюс QA/DevOps на полставки. **Около 10 недель** до эксплуатации на 100 ПК, включая пилот.

### 10.2. Этапы

**Этап 0 — основа и главный технический риск (неделя 1)**
- Репозиторий и CI: сборка агента (официальный Go и форк; x86, x64, arm64), сервера и SPA; линтеры (golangci-lint, eslint), `govulncheck`, тесты.
- Контракт API v1 и схема БД v1 (этот документ) — ревью командой и службой ИБ.
- Стенд: ВМ с Win7 SP1 x86/x64, 8.1, 10 22H2, 11 23H2/24H2, Server 2019/2022; PostgreSQL.
- **Прототип агента на Win7 x86:** служба, WMI, TLS 1.3 до тестового сервера.
- *Готово, когда:* прототип работает службой на всех ОС стенда.

**Этап 1 — «данные идут» (недели 2–3)**
- Агент: служба, конфигурация, регистрация, DPAPI, сбор CPU, RAM и томов, отправка, буфер, повторы, журналы.
- Сервер: Agent API (enroll, metrics, config), токены, приём в партиционированные таблицы, `device_state`, задача партиций.
- UI: вход, список устройств.
- *Готово, когда:* 10 ВМ 72 часа отправляют данные без пропусков; агент занимает ≤ 30 МБ RAM; после двухчасового разрыва связи данные досланы.

**Этап 2 — инвентаризация и графики (недели 4–5)**
- Агент: WMI (железо, диски, сеть), реестр (ПО), хэш снимка.
- Сервер: приём снимков, нормализация ПО, сравнение, `inventory_changes`; агрегаты и очистка по срокам хранения.
- UI: карточка ПК, графики, каталог ПО, «где установлено», выгрузка в CSV.
- *Готово, когда:* на 5 эталонных ПК инвентаризация совпадает с ручной проверкой: железо — с документацией, ПО — с «Программами и компонентами».

**Этап 3 — алерты, доступ, аудит (недели 6–7)**
- Правила (создание, изменение, удаление), движок, offline, гистерезис, подтверждение, повторы; каналы email и webhook с повторами и тестовой отправкой.
- Пользователи и роли, токены регистрации в UI, журнал аудита с просмотром, настройки.
- *Готово, когда:* «C: < 10 %» на тестовой ВМ приводит к письму и webhook не позже чем через 5 минут, после очистки диска алерт закрывается; все действия администраторов — в аудите.

**Этап 4 — готовность к эксплуатации (недели 8–9)**
- MSI агента (x86, x64, arm64, выбор сборки по ОС), ZIP сервера с командами `init` и `service install`, подпись кода.
- Безопасность: проверка TLS, чек-лист OWASP ASVS уровня 2 для веб-части, fuzz-тесты парсеров Agent API, `govulncheck` и `npm audit` в CI, согласование со службой ИБ.
- Нагрузка: симулятор 2 000 агентов в течение суток (запас ×20).
- Регламенты: установка, обновление, резервное копирование и восстановление (с фактическим восстановлением), диагностика WMI.
- Совместимость с корпоративным антивирусом.

**Этап 5 — пилот и раскатка (неделя 10)**
- Пилот на 10–15 ПК → исправления → раскатка волнами через GPO или SCCM.

### 10.3. Критерии готовности MVP

| Критерий | Значение |
|---|---|
| ОС агента | Windows 7 SP1, 8.1, 10, 11 (x86, x64; arm64 — Windows 11) |
| Свежесть метрик в UI | ≤ 2 мин |
| Статус online/offline в списке | ≤ 3 мин |
| Уведомление по алерту | ≤ 5 мин после выполнения условия правила (с учётом его окна) |
| Свежесть инвентаризации | изменения ПО — ≤ 1 ч; полный снимок — ≤ 24 ч |
| Ресурсы агента | RAM ≤ 30 МБ, CPU ≤ 0,5 % в среднем, трафик ≤ 2 МБ в сутки |
| Безопасность | только TLS 1.2/1.3; все эндпоинты, кроме `/healthz` и `/readyz`, требуют аутентификации; все действия администраторов — в аудите |
| Эксплуатация | резервная копия восстановлена на стенде; регламенты переданы ИТ-отделу |

### 10.4. Риски

| Риск | Вероятность / влияние | Как снижаем |
|---|---|---|
| Сборка для Win7 зависит от стороннего форка Go | средняя / высокое | прототип в первую неделю; форк только для legacy-сегмента; закреплённая версия с контрольными суммами; запасной вариант — последний официальный Go с поддержкой Win7 (1.20) как временная мера до вывода Win7 |
| Повреждённый WMI на старых ПК | высокая / среднее | таймауты, частичные снимки с `errors[]`, ПО — из реестра, инструкция по восстановлению WMI |
| Антивирус блокирует Go-бинарник | средняя / среднее | подпись кода, исключение в корпоративном антивирусе, отправка образцов вендору |
| Дубли устройств из клонированных образов | средняя / низкое | `agent_uid`, подсказки о совпадении MachineGuid, объединение в UI; sysprep при подготовке образов |
| Шум алертов | средняя / среднее | окна, гистерезис, дедупликация, фильтр важности на канале, подтверждение |
| Утечка токена регистрации из SYSVOL | средняя / низкое | срок и лимит использований, режим одобрения, аудит регистраций |
| Расхождение часов на ПК | средняя / низкое | коррекция на сервере, предупреждение в UI |
| Рост объёма метрик | низкая / среднее | партиции, сроки хранения и агрегаты с первого дня |

### 10.5. После MVP

- **v1.1:** вход через AD/LDAP и TOTP; UI истории изменений и алерты на изменения (ПО из «чёрного списка», уменьшение RAM, замена диска); шаблоны для Telegram, Mattermost, Teams; окна обслуживания; состояние дисков по S.M.A.R.T. (`MSStorageDriver_FailurePredictStatus`, `MSFT_PhysicalDisk.HealthStatus`); установленные обновления Windows и дата последнего обновления; статус BitLocker; отправка аудита в SIEM; MSI для сервера.
- **v1.2:** отчёты в XLSX и рассылки; API-токены для интеграций (CMDB, Service Desk); восстановление на момент времени (архив WAL); пакет сервера для Linux и Docker-образ.
- **Масштабирование:** до ~5 000 ПК — вертикально (отдельная ВМ для PostgreSQL, более короткое хранение сырых метрик). Дальше — несколько экземпляров сервера за балансировщиком (River корректно работает на нескольких узлах), NATS JetStream перед записью метрик, TimescaleDB или отдельная TSDB для метрик.
